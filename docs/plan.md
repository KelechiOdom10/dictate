# Ship one system, not four projects

The practical answer is to stop planning four projects and build one system in four phases: a two-week Hex dictation clone as a warm-up, one week upgrading footy-ai with behavioural evals and tracing, six weeks building Dash with exactly three connectors and a 150-query gold set, then seven weeks pointing that retrieval spine at your own messages as Jarvis. You are not a beginner — footy-ai already contains a custom `LanguageModelV1` test double, a deterministic pre-classifier, and Zod-constrained query plans, which puts you ahead of most working engineers — so the 16 weeks buy measurement, retrieval quality, permissions and memory, not LLM literacy. Everything runs on **$0–10/month**: local Whisper for Hex, local embeddings, Gemini's free tier for public-data evals, and a paid key only for Jarvis, because personal messages must not go to a tier that trains on inputs. The binding constraint is not tokens but rate limits and the fact that **no free always-on host exists in late 2026**. Your job-ready artifact is the eval table and the failure gallery, not the demo, and the one decision that most determines the outcome is whether you publish the numbers when they are unflattering.

## You already shipped the loop; the gap is measurement

The `footy-ai` repository is not a beginner's project, and any plan that starts with "call an LLM API" is wasted on you. It routes natural language into a typed query plan, compiles that plan to SQL, validates it against the database, and renders a widget — with an explicit design rule that the model chooses the query but never produces the statistics. Tool parameters are Zod-constrained, with a documented workaround for the OpenAI `z.discriminatedUnion` → `anyOf` rejection: a flat schema plus `QueryPlan.parse` to narrow. A deterministic classifier short-circuits known intents before any model call. Most tellingly, a custom `EchoProvider` implements the Vercel AI SDK's `LanguageModelV1` interface so the agent loop is unit-testable with no model and no network — a technique that appears in very little tutorial material and in a great deal of production code ([your GitHub](https://github.com/KelechiOdom10)). `kelechi-engineering-system` goes further: routes, skills, hooks, evidence ledgers and cross-CLI adapters, with a `skills/` tree and its own marketplace manifest. You author `SKILL.md`; you do not consume it.

The weaknesses are equally visible and they are all of one kind. The model is hardcoded to `gpt-4o-mini` with no routing, no cost model and no fallback. There is no tracing, so a bad answer leaves no evidence of which step produced it. The tests grade *parsing* — plan shape, SQL compilation, payload shape, executor behaviour — not *outcomes*, so nothing in the suite would catch a correct query that returns a statistically misleading answer. The system prompt is a large string constant inside a service file rather than a versioned artifact. There is no retrieval and no memory beyond conversation state. In other words: you have built the loop and the type system, which is the part most people never get right, and you have not built the measurement layer, which is the part that separates a demo from an engineering claim.

That ranking matters because it tells you what to skip. This report does not cover API basics, TypeScript architecture, prompt-writing, deployment, queues, or why tools are structured outputs — you demonstrably know all of it. It covers the seven things your public work does not yet show:

| Rank | Gap | What's missing today | Where it gets closed |
|---|---|---|---|
| 1 | Behavioural evals | Tests grade plan parsing and SQL compilation, not answer quality or refusal behaviour | Weeks 3, 8, 15 |
| 2 | Retrieval as a measured discipline | No retrieval in footy-ai; DocuMind's search was the part you judged insufficient | Weeks 6–8 |
| 3 | Tracing, cost model, routing | One hardcoded model, no spans, no per-query cost or latency | Weeks 3, 7 |
| 4 | Authorisation and approval semantics | Single-tenant, no ACL, no human-in-the-loop state | Weeks 5, 8, 11 |
| 5 | Memory and entity identity | Conversation state only; nothing that knows who "my brother" is | Weeks 10, 13 |
| 6 | Python literacy for the tooling layer | One Python repo; the serious eval and serving tools are Python | Weeks 4–16, 10–15h |
| 7 | Theory from tokenisation to inference economics | Not visible publicly, and worth ~40 hours, not 400 | Scheduled behind the build |

The theory row is last deliberately. You cannot debug a retrieval regression by knowing how BPE merges work, but you cannot reason about *why* a 200K-token context is not a substitute for retrieval, or why cached input tokens change your unit economics by an order of magnitude, without it. That is a 40-hour purchase, taken in two-hour slices while something is building, and it is the entire theory budget ([Source](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

## One system, four phases, one new hard idea each

Your worry that four projects is too much is correct, and the resolution is not to cut one — it is to notice that three of them are the same system wearing different clothes. Ingest → normalise → index → retrieve → cite → act with approval → measure is one architecture, and it is the thing you are actually learning to build. Hex is not part of it at all (it is an OS-integration exercise with local speech-to-text and no model API), footy-ai is a single-purpose instance of the measurement layer, Dash is the general spine, and Jarvis is that spine pointed at iMessage and exported bookmarks. Each phase ships and adds exactly one concept you do not yet own: **latency** (Hex), then **measurement** (footy-ai), then **retrieval quality and permissions** (Dash), then **memory and authority** (Jarvis).

## Five gates that keep learning in front of shipping

The hour split above is roughly 228 build to 40 theory, and that ratio will not survive contact with reality. Build pressure wins every week, and the thing it eats is the explaining. Intention does not protect learning; gates that fail loudly do.

| Gate | When | Fails if |
|---|---|---|
| **Predict before measuring** | Before every eval run | You cannot state the number you expect and the mechanism you expect to cause it |
| **Hand-roll, then framework, then diff** | Each layer, once | You adopted a framework without replacing one first |
| **Teach-back** | End of each phase | You need a library or product name to explain the mechanism |
| **Rejection log** | Every non-trivial decision | You cannot name the alternative you rejected and why |
| **Hard stop** | At each phase's hour budget | You kept building past the budget to avoid explaining it |

**Predict before measuring.** Two minutes per run: the metric you expect, the mechanism, the amount of variance you would call noise. Prediction error is the learning metric, because it is the only one that does not flatter you. A week where every prediction was right is a week where you learned nothing about the system.

**Hand-roll, then framework, then diff.** You did this with the agent loop and the `EchoProvider`. Repeat it deliberately: naive retrieval before contextual chunking, a raw stdio MCP server before any helper, a hand-written reranker before a hosted one. The one-page diff — "here is what the framework decided for me" — is the lesson. A framework you adopted teaches nothing; a framework you replaced teaches everything.

**Teach-back.** Eight hundred words per phase, mechanism only, no library names and no product names. If you cannot explain tracing without naming a tracing vendor, you have an integration, not an understanding.

**Rejection log.** One paragraph per decision: what you chose, what you rejected, the evidence that separated them. This is also your interview script, because it is the only artifact you will produce that demonstrates judgement rather than output.

**Hard stop.** At the phase's hour budget you stop building in whatever state it is in, and the remaining hours go to explaining it. Unfinished code with a real explanation beats finished code without one, and the second kind is what everyone else has.

The reason all five are necessary is uncomfortable: the tooling is now good enough that you can ship things you cannot explain. That is the specific failure mode for someone at your level — not lack of ability, but the ease of outsourcing judgement. `footy-ai` is strong for the opposite reason: you authored the constraint, so you can defend every line of it.

The counterpart to all of this is a SOTA list that is deliberately short. **Build side:** the coding agent as primary surface with spec and context files doing the work; context engineering over prompt engineering; harness design (tools, hooks, skills, permissions) as the real substance; model portfolios rather than one model, with routing decided by measurement; agentic retrieval over static pipelines, with hybrid plus contextual chunking plus reranking as the floor; OpenTelemetry GenAI spans for tracing; durable execution and approval gates for anything with side effects. **Learn side:** production source over courses, small reimplementations diffed against a reference, papers figures-first in 45 minutes, and published evals over published demos. **Ignore side:** framework churn, agent platforms as a learning path, vector-database shopping, fine-tuning as a first move, prompt tricks, and multi-agent architectures before single-agent evals. Note also that most framework comparisons circulating are vendor-published — there is no independent benchmark, so treat every "X beats Y" table as marketing until you have run it yourself.

## Phase by phase: what to build and the gate you must pass

### Weeks 1–2: Hex earns its place by being useful, not educational

The AI here is a local streaming speech-to-text model — WhisperKit or `whisper.cpp` on Metal, or Parakeet via MLX — and it costs nothing per minute because nothing leaves the machine. That is also the honest reason it is a warm-up: the interesting engineering is macOS, not models. Build in this order. First, a permission spike: request Accessibility and Screen Recording via TCC, handle denial gracefully, and confirm you can read the focused element's role and value. Second, a global hotkey that does not steal focus — a `CGEventTap` on a modifier combination or `RegisterEventHotKey`, with the overlay rendered in a non-activating `NSPanel`. Third, audio capture at 16 kHz with a ring buffer that starts before the key is released, so the first phoneme is not lost. Fourth, streaming transcription with a partial-result callback, so text appears while you speak. Fifth, insertion: `AXUIElement` set-value where the field supports it, `CGEvent` unicode keystrokes where it does not, clipboard-paste with restore as the fallback. Sixth, the annotation canvas and the scrollable artifact export — this is ordinary 2D drawing and is where most of week 2 goes. Seventh, signing and notarisation, because an unsigned build that re-prompts for permissions every launch will lose to Hex on convenience and you will stop using it.

Choose the stack you will actually finish: Tauri 2 with a Rust audio/STT core and a web canvas, or straight SwiftUI if you want the smallest permission surface. Do not build a cross-platform abstraction. The gate is behavioural, not technical: **five consecutive days of real use in place of Hex**, p95 key-release-to-text under 1.5 seconds on your machine, and word error rate measured on twenty of your own recordings rather than asserted. Write one page on the permission model and the insertion fallbacks — that page is the interview answer for "tell me about a time you fought the platform", and it is genuinely rare.

### Week 3: footy-ai becomes the cheapest place to learn eval discipline

Rebuilding footy-ai would be the most expensive mistake available to you, because the hard unknown — can a model turn a question into a validated query plan — is already solved in that repo. What is unsolved is whether the answers are any good, and football statistics are the ideal domain to find out: you understand the ground truth, the data is public, and a wrong answer is objectively wrong. Five changes, in order.

Build the gold set first: **60–80 real questions** with expected result sets, not expected SQL strings. You already validate SQL against the database, so grade by result-set equality and by whether the rendered widget is the right shape. Label each case with a category — single-stat lookup, comparison, time series, ambiguous, unanswerable — because the aggregate will hide the category that is broken. Then build the harness: five runs per case, reporting **pass@1 and pass^3** (at 75% per-trial success, pass^3 is about 42%, which is the number a user experiences), plus per-category breakdown, tokens, dollars and latency. Third, add tracing with OpenTelemetry GenAI semantic conventions or a self-hosted Langfuse, one span per model call, tool call and SQL execution, keyed by run id ([semconv](https://opentelemetry.io/docs/specs/semconv/gen-ai/); [Langfuse](https://github.com/langfuse/langfuse)). Fourth, replace the hardcoded `gpt-4o-mini` with a routing policy: a cheap model for plan generation, escalation on validation failure or low confidence, and a measured table of accuracy against cost and latency for each arm. Fifth, move the system prompt into `prompts/` as a versioned file with a content hash recorded in every trace, so a prompt change shows up in the eval diff rather than in a user complaint.

The gate: `make eval` reproduces a table in the README from a clean checkout, with n=5 and a variance column; ten real traces in a failure gallery with a one-line diagnosis each; a written routing decision that names the accuracy delta you accepted for the cost delta you bought; and a prompt hash in the trace. This week is the highest leverage in the plan per hour spent, because eval discipline learned in a domain you already understand transfers to every later phase, and because "the candidate starts with evals" is the single most repeated hiring signal in the field ([Field Guide](https://github.com/alexeygrigorev/ai-engineering-field-guide/blob/main/interview/questions/06-home-assignments.md)).

### Weeks 4–9: Dash, with three connectors and a number that has to move

Dash is the centrepiece because it is the only project that forces retrieval quality, permissions, citations and cost into one artifact. Cap it at **three connectors**, chosen for contrast rather than coverage: local files (Markdown and PDF), Google Drive or Notion, and a chat-shaped source such as a Slack export. The cap is not modesty; after the second connector, connector work teaches nothing new and the surface area grows without bound. Write the connector interface before the second implementation: `list(cursor) → records[]`, `fetch(id) → blob`, `acl(record) → principals[]`, `cursor() → opaque`. If a fourth source is ever needed, it should be an afternoon, not a phase — and that property is the actual deliverable.

The schema is the part to get right once, because Jarvis inherits it. A `documents` table keyed by `(source, source_id)` with a content hash, timestamps, a URL and an `acl` array; a `chunks` table with ordinal, text, a `contextual_text` field, token count, a `tsvector`, and a `vector` column; a `sync_cursors` table per connector; a `runs` table for traces. Postgres with pgvector and `tsvector` is sufficient — you already know Postgres and Drizzle, and adding a dedicated vector database buys nothing at this scale. Ingestion is a BullMQ job per document with an idempotent upsert on the hash, so a re-sync is a no-op and a partial failure is retryable.

Week 6 is deliberately unglamorous: measure BM25 alone, then dense embeddings alone, and write both numbers down before improving anything. Week 7 is where the quality comes from. Chunk to 300–500 tokens on structural boundaries, then generate a 50–100-token situating blurb per chunk from the parent document and index both the blurb and the text — Anthropic's contextual retrieval work measured a **35% reduction in top-20 retrieval failures from contextual embeddings alone, 49% with contextual BM25 added, and 67% when a reranker took 150 candidates down to 20** ([Source](https://www.anthropic.com/news/contextual-retrieval)). The one-time cost was about **$1.02 per million document tokens** at Haiku pricing with prompt caching; with a local model or Gemini's free tier it is effectively zero and merely slow, which is the right trade for an offline job. Fuse rankings with reciprocal rank fusion, retrieve 150, rerank to 20 with a local cross-encoder such as `bge-reranker-v2-m3`, and keep the four-row ablation table: BM25, dense, hybrid, hybrid+contextual+rerank. Pick the configuration on recall@10, not on how modern it feels.

Week 8 is the week that makes the project defensible. Expand the gold set to **150 hand-labelled queries** with graded relevance: 60 single-source fact lookups including exact identifiers and dates, 30 cross-source questions where the answer needs two connectors, 25 temporal questions ("what did I decide about the pricing model in March"), 20 aggregation questions, and 15 that are unanswerable and must produce a refusal. Report **recall@10 as the primary metric**, with nDCG@10 and MRR as secondary, plus abstention accuracy on the 15 negatives. Alongside it, write **20 permission tests** where a query issued as one principal must not return another principal's document, and assert the absence at three points: the retrieval result set, the citation list, and the answer text. Add one poisoned document containing an instruction to reveal all documents, and assert it is treated as data. This is the part almost nobody builds, and it is exactly what a take-home rubric and a system-design interview probe for ([OWASP LLM01](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)).

Week 9 turns the index into a product-shaped thing: an answer synthesis step with structured output — `{answer, citations[], confidence, refused}` — where every claim maps to a chunk id and a deep link, a refusal path when the top reranked score falls below a threshold you chose from the data, a Next.js UI that streams the answer and shows sources and latency, and a cost/latency panel. The gate: recall@10 beats the BM25 baseline by at least 15 points absolute and clears **0.75** (a design target, not a measured norm), zero leaks across the 20 permission tests, every answer cites, and the ablation table is in the README with the loser configurations still in it.

### Weeks 10–16: Jarvis is the same spine pointed at your life

Jarvis is not a fourth project. It is the Dash index with two new sources, an entity graph, and an authority model, and if you find yourself rebuilding ingestion you have taken a wrong turn. Start with the sources that legitimately exist. WhatsApp has no access path you should use — the Business API is for businesses with template approval, and unofficial libraries breach the terms and risk the account — so drop it, as agreed. X/Twitter bookmarks should come from the account export rather than the API, which is gated and priced. iMessage is feasible on macOS: `~/Library/Messages/chat.db` under Full Disk Access, copied along with its `-wal` and `-shm` companions before reading so you do not fight SQLite locking, opened read-only. Normalise both into the Dash schema with `source = 'imessage' | 'x_bookmarks'`, and reuse every downstream component.

Identity resolution is the first genuinely new idea. Build a `person_alias` table mapping handles, phone numbers, emails and nicknames to a `person_id`, sourced from Contacts, and resolve "text my brother" by lookup rather than by model inference. When a name is ambiguous — two Alexes — the correct behaviour is to ask, not to guess, and that is an authority decision expressed in code, not in a prompt. Test it with 25 real people including five deliberately ambiguous names.

The tools are five and no more: `search`, `get_thread(person, window)`, `draft_reply(person, intent)`, `create_reminder`, `resolve_person`. Drafts go to a queue, never to a send. Version one copies to the clipboard; version two, if you ever add it, sends only after an explicit approval row is written with who approved what and when. That is 12-Factor's "contact humans with tool calls" made concrete, and it is the difference between an agent and a liability ([12-Factor](https://github.com/humanlayer/12-factor-agents)).

The safety filter is a classification problem with its own metrics, not a prompt. Label **250 items** from your own bookmarks and messages into six classes — safe, spam, scam, harassment, adult, self-harm — then fit a TF-IDF plus logistic regression baseline before touching an LLM. Conventional classifiers frequently match or beat an LLM judge at a fraction of the cost and latency, and having the baseline makes the LLM's contribution measurable rather than assumed ([Applied LLMs §1.4.2](https://applied-llms.org/)). Report per-class precision and recall, **PR-AUC rather than ROC-AUC** because the classes are imbalanced, a calibration curve, and the confusion matrix at the threshold you shipped. Choose the threshold from the cost asymmetry — missing a scam is worse than a false flag — and write that reasoning down. This is the phase where you learn that "the model decides" is not an architecture.

Memory is the last new idea: conversation state in Postgres, plus an explicit `notes` table the agent can write to and retrieve from, plus compaction at around 60% of the context budget. The test set is the one you actually care about: 100 personal queries, half of them retrieval ("that tweet where I said the thing about hiring"), half of them action ("draft a reply to the thread about the wedding"). Measure recall@10 on the first half and rubric-graded draft quality on the second, with a judge calibrated against 40 of your own labels and a reported agreement figure.

The gate: zero unapproved sends anywhere in the suite, including a scripted attempt; per-class safety metrics at a justified threshold; 25/25 identity resolution; recall measured on 100 personal queries; and a cost cap enforced in code that degrades rather than breaks when a provider returns 429.

The consolidated non-negotiables, so you can check them in thirty seconds on a Sunday evening:

| Phase | All of these must be true before the next phase starts |
|---|---|
| Hex | Five consecutive days of real use; p95 release-to-text measured; WER measured on 20 of your own clips; one page on permissions and insertion fallbacks |
| footy-ai | `make eval` reproduces a table with n=5 and variance; 60–80 labelled questions; 10-trace failure gallery; routing decision with measured cost and accuracy; prompt hash in every trace |
| Dash | 150 labelled queries with graded relevance; recall@10 reported against a BM25 baseline; four-row ablation table; 20 permission tests with zero leaks; one poisoned document; every answer cites; p50/p95 and $/query |
| Jarvis | 25/25 identity resolution including ambiguous names; 250 labelled safety examples with per-class precision/recall at a justified threshold; zero unapproved sends; 100 personal queries measured; spend cap that fails closed |

If a phase overruns by more than three days, ship the smaller version and move on. The sequence's value is the order of the ideas, not the completeness of any one phase — and an unfinished layer teaches nothing, while a thin one still teaches the concept it exists to teach.

## Forty hours of theory, scheduled behind the build

The theory budget is **40 hours**, taken in two-hour slices after the corresponding thing exists, because a paper read before you have the observation it explains is entertainment. The one exception is Karpathy's 3.5-hour "Deep Dive into LLMs like ChatGPT", which is the best hours-per-concept artifact in the field and belongs in week 1 as background while you fight TCC permissions ([Source](https://www.youtube.com/watch?v=7xTGNNLPyMI)).

Learn to read a paper in 45 minutes and never read one any other way: abstract, then figures and captions, then the results table, then the limitations, then the method section if a figure did not make sense. Skip proofs and appendices on a first pass. The test of whether you read it is whether you can state what the authors measured, what they did not, and what decision of yours it would change. That test is also how you should judge every "new model beats GPT" claim you see for the rest of your career.

The cuts are as important as the list. **LLM101n is a trap**: the repo was archived in August 2024, its own README says the course does not exist, and Karpathy confirmed in October 2025 that it is experiencing scope creep ([repo](https://github.com/karpathy/LLM101n); [post](https://x.com/karpathy/status/1977763719812710501)). Its de-facto successor is nanochat, which trains a GPT-2-class model for about **$48 on eight H100s in roughly two hours** and is genuinely excellent — but it is not free, it is not required for this plan, and it belongs in month six if you find you want the training layer rather than needing it ([nanochat](https://github.com/karpathy/nanochat)). fast.ai is the 2022 edition and thin on LLMs. CS336 is a 200-hour, five-unit, implementation-heavy course whose prerequisites include prior ML coursework; take lectures **1, 10, 12, 15–16** and skip the Triton, FlashAttention, distributed-training and Common Crawl dedup assignments, which are academic tourism for this role ([CS336](https://cs336.stanford.edu/spring2025/)). DeepLearning.AI short courses are worth two or three at most and carry no hiring signal. The 500-lesson, ~342-hour "AI Engineering from Scratch" curriculum is a trap as a plan, whatever its individual lessons are worth ([repo](https://github.com/rohitg00/ai-engineering-from-scratch)).

Explicit tourism, to be recognised and skipped: hand-derived backpropagation, SVM dual forms, PPO/GRPO objective maths, Triton kernels, ZeRO/FSDP, data dedup pipelines, and training anything above 1B parameters. RLHF and RLVR *consequences* are load-bearing; their *algorithms* are not. Quantisation gets two hours, because it matters for reading model cards and running local models, and no more ([mlabonne](https://mlabonne.github.io/blog/posts/Introduction_to_Weight_Quantization.html)).

Classical ML gets 8–12 hours and statistics gets more of it than algorithms. The reason is directly practical for you: the safety classifier needs a TF-IDF plus logistic regression baseline, the eval table needs a bootstrap confidence interval, and the routing decision needs to distinguish a real accuracy delta from noise. Skip CS229 entirely. A confusion matrix you can defend beats a derivation you cannot use.

## Stay in TypeScript; learn enough Python to read the field

Do not abandon TypeScript. Your leverage is that you can ship a Next.js frontend, a Postgres schema, a BullMQ worker and a Cloudflare deployment without learning anything new, and that is precisely the part of agent engineering most learners cannot do. The stack decisions follow from that.

| Layer | Use | Why | Ignore |
|---|---|---|---|
| Agent loop | Your own loop over the Vercel AI SDK (`streamText`, `tool()`, `ToolLoopAgent`) | You already have the raw loop and an `EchoProvider` test double; a framework would hide the thing you are best at | LangGraph, CrewAI, Agno for this build |
| Orchestration | Postgres run tables + BullMQ + explicit state machine | Your existing primitives already give durable execution, retries and resumability | Framework-managed memory; graph runtimes until you need branching |
| Tools/interop | MCP TypeScript SDK; one server exposing the Dash index | The one protocol worth deep investment, and TS is first-class | A2A beyond a read; AGNTCY |
| Retrieval | Postgres + pgvector + `tsvector`, reciprocal rank fusion, local cross-encoder reranker | You know Postgres; a dedicated vector DB is unjustified at this scale | Pinecone/Weaviate/Qdrant shopping |
| Embeddings | Local `bge-m3` or `embeddinggemma` via Ollama | Free, private, no rate limit, and re-embedding is the most common hidden cost | Paid embedding APIs for a personal corpus |
| Evals | `promptfoo` for CI, plus ~200 lines of your own harness for recall and permission tests | promptfoo is TypeScript-native and CI-shaped; the custom harness is where the learning is | DeepEval/Ragas as the primary harness (Python, and you would be reading them not writing them) |
| Observability | OpenTelemetry GenAI semconv → self-hosted Langfuse | OTel keeps traces portable; Langfuse is open-core and you can run it in Docker | Vendor SDKs that own your instrumentation |
| STT | WhisperKit / `whisper.cpp` / Parakeet MLX | Local, streaming, $0/minute | Cloud STT for Hex |
| Hosting | Cloudflare Workers + D1 for a stateless demo; a $2–5 VPS for anything long-running | You already know Workers; the 10 ms CPU cap is fine because model calls are I/O | HF Spaces as a free host |

Everything in that table is MIT or Apache-2.0 except Langfuse and Arize Phoenix, which are open-core and reported by GitHub as `NOASSERTION`, and the model APIs themselves; verify the licence behind any `NOASSERTION` repo before you depend on it commercially. The rest of the field's "open source" is frequently open weights under a bespoke licence, which is a different claim — Llama's community licence carries a 700M-MAU trigger, Gemma requires you to flow its use restrictions into your own terms, and the OSI has publicly rejected both as open source ([OSI analysis](https://safeguard.sh/resources/blog/open-weights-vs-open-source-ai-definition)). For a portfolio project none of this bites; for anything with a payment link, read the two clauses.

Framework verdicts, compressed: start from the raw loop (already done), then use the Vercel AI SDK because it is the lowest-friction path from your existing code, then read LangGraph's model only if you need branching, checkpointing and interrupts — and even then, given that you can write durable state in Postgres, you may reasonably decide you do not. Skip Swarm (superseded by the Agents SDK), AutoGen (maintenance mode), Flowise (archived), and LlamaIndex as an agent framework (it has repositioned as a document-processing platform). `anthropics/courses` and `langchain-ai/open_deep_research` are archived; do not start from either. If you want one Python framework to read rather than use, read Pydantic AI for its write-time validation and its OTel integration; the mental model transfers directly to Zod.

MCP is the exception to "do not learn new infrastructure". Read the spec's architecture, transports and security sections rather than the whole document, then write one stdio server exposing four tools over the Dash index — `search_documents`, `get_document`, `list_sources`, `ask` — and connect it to both Claude Code and your own client. Add one remote server with auth afterwards. This teaches tool schemas, capability negotiation, consent and the security model in a weekend, and a published server is a verifiable artifact in a way that a demo is not ([spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25); [AAIF donation](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/)). Agent Skills and `AGENTS.md` you already live inside; spend an hour on the spec's progressive-disclosure mechanism and then port one real workflow — your Dash eval loop — into a skill, so the harness runs it for you. That is a bridge from what you know to the standard, not a lesson from zero ([agentskills.io](https://agentskills.io/); [agents.md](https://agents.md/)).

The Python question deserves a straight answer, and it starts with the fact that TypeScript is genuinely first-class for the parts you are building: the Vercel AI SDK's agent classes, Mastra's workflows and eval scaffolding, the MCP TypeScript SDK, and Cloudflare's Agents SDK on Workers. The serious tooling layer is Python: vLLM for serving, Pydantic AI for typed agents, Inspect for rigorous evals, DeepEval and Ragas for eval plumbing, Unsloth and TRL for fine-tuning, nanochat and the CS336 assignments for training. That is a real gap and it is a gap in *reading*, not in *building*. Spend **10–15 hours**: learn `uv`, `pytest`, `pydantic` and `asyncio` well enough to be dangerous; read the vLLM and Pydantic AI source where it matters; run one real eval in Inspect so you have used the tool that UK AISI built; and write one 150-line script that calls a model and scores outputs. Do not learn Django, pandas or notebook culture. Do not rewrite a service in Python. If you later want inference or serving work, that is a different job with a different gap, and you will know when you want it.

## Free tiers are a gift with a revocation clause

The 2025 advice is now wrong, and most of it is still circulating. **GitHub Models was fully retired on 30 July 2026**, taking the only free access to frontier closed models with it. **Hugging Face zeroed free Inference Providers credits on 7 October 2026**, and creating a Gradio or Docker Space now requires PRO at $9. **Cerebras has no free tier** — $5 of credit after a verified card, expiring in 30 days. Groq's free plan is 30 RPM and 200K tokens/day, which is roughly **150–300 agent turns per month**, about 25 minutes of generation at its own 8K TPM ceiling. OpenRouter's `:free` models allow **50 requests per day**, which is one medium conversation, and a `:free` model inside a fallback array will silently bill you when it rate-limits and the router falls through. Gemini's AI Studio tier is the only genuinely generous one, it trains on your inputs outside the EEA, UK and Switzerland, and **Google no longer publishes its free-tier rate table** — it lives in the AI Studio console, so any blog quoting RPM numbers is quoting 2025 ([rate limits](https://ai.google.dev/gemini-api/docs/rate-limits); [HF pricing](https://huggingface.co/docs/inference-providers/en/pricing); [Cerebras](https://inference-docs.cerebras.ai/support/rate-limits); [OpenRouter](https://openrouter.ai/docs/api/reference/limits)).

| Provider | Free tier, November 2026 | Card | Trains on inputs | Role in this plan |
|---|---|---|---|---|
| Gemini AI Studio | Flash/Flash-Lite free; limits unpublished, per-project | No | **Yes** | Public-data evals, synthesis for Dash |
| Groq | 200K TPD, 200–300 turns/month | No | Not stated | Fast iteration on the loop only |
| OpenRouter `:free` | 50 req/day, 1,000 after a one-time $10 | No | Varies | Fallback for non-private experiments |
| Cloudflare Workers AI | 10,000 neurons/day; 7 models need paid | No | **No** | Small classifications, embeddings at low volume |
| HF Inference | None since 7 Oct 2026; PRO $9 gives $2 | No | Upstream | Skip |
| Cerebras | No free tier; $5/30 days | **Yes** | No | Skip |
| GitHub Models | Retired 30 Jul 2026 | — | — | Skip |

Two things follow. First, phase-by-phase: Hex costs **$0 forever** because the model is local. footy-ai's eval runs are 600–800 agent turns, which Groq cannot absorb but Gemini can, and football data is public so the training-on-inputs term is irrelevant. Dash needs local embeddings (free, no rate limit) and one contextual-chunk generation per chunk — 10,000 chunks at 150 output tokens is 1.5M tokens, which is a few days of Gemini free tier or one overnight run of a local 8B model. Jarvis is the phase where the free tier is disqualified, because your messages are exactly the data you must not send to a provider that trains on inputs: local model for classification and embeddings, and a paid key for synthesis.

Second, the arithmetic is not the constraint. At 8K input and 1K output per turn, ten turns a day on a $0.10/$0.50-class model costs about **$0.39/month**; a 50-user demo costs about $1.30. The median paid model charges $1.80 per million output tokens across 337 models, and the cheapest usable tier sits roughly 100× below the frontier's $10/$50 ([llmbenchmark.ai](https://llmbenchmark.ai/pricing)). What actually binds is rate limits and hosting. So the honest budget is **$0 for weeks 1–9**, then **$5–10/month** for Jarvis: a $5 Gemini Tier 1 prepay or a one-time $10 OpenRouter top-up, plus $2–5 for a Fly or Railway worker only if you need the thing awake.

Hosting is where the free-tier story collapses. There is **no free always-on host**: Cloudflare Workers allows 100K requests/day but caps CPU at 10 ms per request, Vercel Hobby is non-commercial personal use only and locks you out for 30 days at the cap, Render's free service spins down after 15 minutes with 512 MB and 0.1 CPU, HF Spaces sleeps after 48 hours and now charges for compute Spaces, and Fly.io has no free tier at all ($1 of credit for 7 days) ([Cloudflare](https://developers.cloudflare.com/workers/platform/pricing); [Vercel](https://vercel.com/docs/plans/hobby.md); [Render](https://render.com/docs/free); [Fly](https://docs.fly.io/about/pricing)). The cheapest credible options are Fly at about $2, Vultr at $3.50, DigitalOcean at $4, and Railway Hobby at $5 ([flaviocopes](https://flaviocopes.com/hosting-free-tiers/)). If you insist on $0: ship a local-only demo plus a recorded three-minute walkthrough, which is what most reviewers will watch anyway, and put a stateless request/response slice on Cloudflare Workers with D1 for anyone who wants to touch it.

Build for revocation, since that is the actual pattern: a free model ID is promotional and expires (Gemini 2.5 Flash and Pro shut down on 1 December 2026; Llama left Groq's free tier in August 2026). Put every model behind one OpenAI-compatible client with a base URL and a model ID in config, fail closed rather than falling through to a paid model, and pin the model and date in every eval report. Prompt caching is the other structural habit: keep the stable prefix — system prompt, tool schemas, connector documentation — first and the volatile content last, which buys up to **90% cost reduction and more than 2× latency improvement** on repeated prefixes ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)).

Local models are a development convenience, not a demo strategy. On a 16 GB Mac, an 8B at Q4 runs at roughly 21 tok/s, a 14B fits with memory pressure, and a 27B at Q4 measures **5.8 tok/s**, which is unusable interactively. Tool-call reliability has a floor at **Q4_K_M**; sub-7B models and untrained 7–13B models fail structurally. And Ollama defaults every model to **4,096 tokens of context**, silently truncating tool schemas — this is the single most common cause of "my local agent is dumb", and some harnesses now refuse to start below 64K ([Ollama context](https://kevinwelter.com/en/blog/qwen-3-8-ollama); [16 GB ceiling](https://github.com/drwjkirkpatrick-web/apple-16gb-local-llm); [tool-calling floor](https://www.promptquorum.com/power-local-llm/best-local-models-tool-calling-2026)). Set `num_ctx` explicitly, bind Ollama to localhost (12,269 instances were internet-reachable in February 2026), and expect eight-step reliability of about 66% even at 95% per step.

## The eval artifact is the portfolio; the demo is not

A hiring manager cannot tell your Dash from the fortieth "chat with your documents" repo in a screenshot, and the take-home data says RAG-over-documents appears in **40%+ of candidate submissions**, which makes it the floor rather than a differentiator ([Field Guide](https://github.com/alexeygrigorev/ai-engineering-field-guide/blob/main/interview/questions/06-home-assignments.md)). What they can read in ninety seconds is a table with error bars and a failure gallery. Ten items, and each one is cheap once the phase exists:

| # | Item | Where it comes from |
|---|---|---|
| 1 | `evals/` with versioned JSONL: `case_id`, `input`, `expected`, `category`, `difficulty`, `source` | Weeks 3, 8, 15 |
| 2 | Everything pinned: model ID, date, temperature/seed, prompt hash, harness commit SHA | Week 3 |
| 3 | Task-level pass/fail plus trajectory checks: right tools, right order, no forbidden tool, step count | Week 3 |
| 4 | Judge calibrated on 40–50 human labels with agreement % and Cohen's κ, judge prompt published | Weeks 9, 15 |
| 5 | Per-category table, never one aggregate | Weeks 3, 8 |
| 6 | N≥5 runs, mean ± range, and a note on what causes the non-determinism | Weeks 3, 15 |
| 7 | Cost and latency per task: tokens in/out, dollars, p50/p95 | Weeks 7, 9 |
| 8 | **Negative results and a 10-trace failure gallery** | Weeks 3, 9, 16 |
| 9 | "What this eval cannot tell you": coverage, judge blind spots, distribution shift | Week 16 |
| 10 | `make eval` reproduces the table, and CI fails on regression | Weeks 3, 8 |

The single highest-trust item on that list is the reversal. "I built five agents, evals showed the multi-agent version cost 4.2× more for two points of accuracy, I removed it and documented why" cannot be produced by a tutorial and is very hard to fake. You will have at least one real reversal by week 9 — probably a reranker that did not pay for its latency, or a contextual-chunking run that helped one category and hurt another — and it belongs in the README, not in your head.

Two framing facts make this worth the hours. Harness choice explains about **5.3% of variance in agent success versus 0.7% for model choice — roughly seven times more** — so the eval is not measuring the model, it is measuring your scaffolding, which is exactly what an employer is buying ([Braintrust](https://www.braintrust.dev/evals/hf-agent-traces)). And in a study of 22 production agent incidents, **about 70% of silent failures were caught by humans looking at output**, not by the 4,000 unit tests or the governance layer, while scanners derived from postmortems blocked **87% of recurrences** ([arXiv 2606.14589](https://arxiv.org/html/2606.14589v1)). That is the argument for reading transcripts and writing a failure taxonomy: the boring artifact is the one that stops the second incident.

Write one page per project, at the end, with a fixed shape: problem and constraint, architecture diagram, the eval table with n and variance, three failures with traces, cost per query, what you would do differently, and what the eval cannot see. Publish it on your own site and cross-post. It travels without you, which a demo does not.

## Hiring is a positioning problem; product is a different bet

### Hiring

You are not trying to become employable; you are a senior engineer at Humaans with five years of shipping and 45 public repos. The risk is being read as "strong web developer who did an AI side project", and the fix is that the artifact leads with measurement rather than with the model. Three things to prepare, not thirty: one project you can defend for 45 minutes including what broke (Dash), a 90-minute build muscle — schema-first tools, loop, ten-case eval, cost estimate, README with trade-offs — rehearsed until the shape is automatic, and DSA at easy/medium, because it has not gone away. The published process data puts the median loop at **four stages**, with take-homes at about **33% of companies** and some agent-specific rounds now run as a three-day build or an AI-assisted coding session ([AI Shipping Labs](https://aishippinglabs.com/blog/ai-engineering-interview-process)). Anthropic's Applied AI loop is a five-stage version of the same shape, including a customer-conversation simulation; treat its reported filter rate as unverified marketing and the structure as real ([Source](https://getperspective.ai/blog/anthropic-applied-ai-engineer-interview-process-frontier-lab-2026)).

Two habits convert. First, write an `ASSUMPTIONS.md` and proceed in any take-home, because "how did you handle ambiguity without asking" is now a scored dimension. Second, have an opinion about frameworks that is grounded in a rebuild you actually did — you will have rebuilt the footy-ai loop with routing and the Dash loop with your own orchestration, so "LangGraph is the right call when you need interruptible durable state, and here is the week I would have saved" is available to you and is not available to someone who has only read the docs.

Open source is worth three months of light, sustained work, not a sprint. The good-first-issue label is often empty on exactly the repos people recommend: **llama_index** ([repo](https://github.com/run-llama/llama_index)) had 12 open, **vLLM** ([repo](https://github.com/vllm-project/vllm)) 14, the **MCP Python SDK** ([repo](https://github.com/modelcontextprotocol/python-sdk)) 6, and **LangGraph** ([repo](https://github.com/langchain-ai/langgraph)) zero, with eight `help wanted`, in the November 2026 snapshot. Search `help wanted` and `documentation` too. The contributions that land are a reproduced bug with a failing test, an error message that cost you an hour, and docs for a path you actually walked. Given your stack, promptfoo, the Vercel AI SDK and the MCP TypeScript SDK are the realistic homes; vLLM is Python and would be a different, slower investment. Skip certificates entirely — completion certificates carry approximately zero hiring signal, and one proctored cloud certification is the maximum if you later target an enterprise.

### Product

Keep this separate from the career plan, because the two have different success criteria and conflating them produces bad decisions in both. On the evidence: **Dash is a crowded market with an IT buyer**. The buyer wants connectors (which you have deliberately capped at three), SSO, retention controls, audit logs and a DLP story — none of which is retrieval engineering, and all of which is a company rather than a project. DocuMind's insufficiency is data about scope, not about demand, but it is also a warning: the second attempt fails the same way if the scope is the same. The gold set is the asset, not the UI; if you ever commercialise, it is the gold set and the permission model that a design partner is buying, and they will want it for their corpus, not yours.

**Hex is the most commercially plausible** of the four, precisely because it is small: consumer-priced, local-first, zero marginal cost per minute, and a privacy story that cloud dictation cannot match because the audio never leaves the machine. It is also the only one where you are the customer, which means support is authentic and the roadmap writes itself. That does not make it a business; it makes it the one with the shortest path from shipped to paid.

**Jarvis is a personal tool** unless the identity and memory layer turns out to be the wedge, and the local-only constraint that makes it trustworthy also caps its distribution. Treat it as the demonstration that the retrieval spine generalises, and as something you will use daily.

Make the product decision **after** week 9, on evidence, not now. The test is concrete: if recall@10 plateaus below roughly 0.75 with three connectors, or permission modelling consumed more than a fifth of the phase, the horizontal thesis is dead and Dash is a portfolio piece — a very good one. If it clears and you can name five people who would pay for it against their own corpus, run a design-partner pilot before writing another connector. That is a two-week test, not a pivot.

## What this report cannot tell you

The hour estimates are design judgement, not measurement. No source benchmarks "hours to competence" for agent engineering, and this plan's 268-hour total is arithmetic from your stated 15–20 hours a week, not evidence that 268 is sufficient. If you have less time than you think — and most people do — cut Hex's annotation polish and its notarisation first, never week 8 or week 15.

There is **no independent, reproducible benchmark of agent frameworks**. Every comparison available is vendor-published, and the one most often cited is written by an observability company selling into the same market. Star counts and release cadence measure attention, not correctness, which is why the framework recommendations here are ranked by learning value and by fit with your existing stack rather than by any performance claim. The same caveat applies to local-model tool-calling percentages: the published tables are author-run, and I found no independent multi-turn agentic benchmark at 16–24 GB.

A2A's current specification version is unconfirmed — the README does not state one — so treat it as a protocol to read, not to build on. Agent identity and authorisation standards are still moving and anything written about them may be superseded within months.

Free-tier numbers are dated November 2026 and change monthly, usually by silent withdrawal rather than announcement. Gemini's free-tier rate limits are not published at all, so the only authoritative source is your own AI Studio console. Hugging Face's ZeroGPU quota is internally inconsistent across its own pages, and Mistral's two official pages contradict each other on whether API access is included in its free mode. Where provider documentation disagrees with itself, this report says so rather than picking a number.

The hiring-signal claims are inference from assignment-frequency data and practitioner commentary, not measured callback rates; no source quantifies what a given portfolio artifact is worth in interviews. The `footy-ai` assessment comes from reading the repository, not from running it — if there are unpublished evals, the ranking changes. And the market assessment of Dash is judgement, not market research; the only honest way to test it is the post-week-9 conversation with five potential buyers.

## Conclusion

The unusual feature of this plan is that three of its four projects are deliberately under-scoped. Hex is allowed to teach you nothing about AI, footy-ai is allowed to be one week, and Dash is forbidden a fourth connector. That is the curriculum: the constraint, not the content, is what converts sixteen weeks into a system rather than four abandoned repositories. Every phase you are tempted to extend is a phase where the marginal week buys polish and the missing week buys the next layer.

Your actual competitive position is narrower and better than "learning AI engineering". Plenty of people can learn to call a model; very few can ship a Postgres schema, a queue, an ACL model and a Next.js surface in the same week, which is what an agent product actually is. What you are buying with these 268 hours is measurement discipline on top of that — the ability to say a number, defend its error bars, show the traces where it failed, and explain what you removed when the evidence said so. That is the scarce skill, and it is the one that survives the next model release. The decision that matters most is not which project you pick. It is whether, in week 9, you publish the recall table when it is worse than you hoped.
